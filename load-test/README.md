# load-test — 부하 시나리오와 베이스라인 측정

관련 이슈 #405. 이 디렉터리는 **빌드 대상이 아니다.** Gradle이 보지 않고 배포에도 들어가지 않는다.

## 이 측정이 답하려는 것

성능을 손대기 전의 기준값을 만든다. **개선은 여기 없다.** 무엇을 고쳤을 때 좋아졌다고 말하려면 고치기 전 값이 있어야 하고, 그 값을 다시 만들 수 있어야 한다.

## 로컬 측정의 경계 — 먼저 읽을 것

이번 측정은 개발 기계에서 돈다. 그래서 **응답 시간의 절대값에 합격선을 적용하지 않는다.**

- 개발 기계는 t3.micro(2 vCPU, baseline 0.2 vCPU 상당)보다 몇 배 빠르다
- MySQL·Redis가 같은 상자 안 docker라 네트워크 왕복이 사실상 0이다
- 여기서 p95가 50ms로 나와도 그건 합격이 아니라 **다른 기계의 숫자**다

대신 **배수**를 본다. 동시 사용자를 두 배로 늘리면 응답이 몇 배가 되는가, 특정 조건을 바꾸면 몇 배로 줄어드는가. 배수는 기계가 달라져도 방향이 유지된다.

### 이번에 확정되는 것과 안 되는 것

- **확정 가능** — 낙찰 팬아웃의 스케줄러 점유(가설 2) · 커넥션 풀 상한(가설 3) · 세션 저장소 왕복 **횟수**(가설 4)
- **의심 근거까지만** — 입찰 잠금 구간에 알림이 얹혀 있는지(가설 1). 직접 증명하려면 알림 발행을 빼고 재야 하는데 그건 코드 변경이라 별도 이슈로 뺐다
- **못 잼** — 세션 저장소 왕복의 **소요 시간**. 로컬 Redis는 왕복이 0에 가까워 실제 환경의 비용이 나오지 않는다

## 실행 절차

### 0. 사전 준비

```bash
brew install k6
```

```bash
cd backend && docker compose up -d
```

### 1. 앱을 측정 프로파일로 띄운다

```bash
cd backend && ./gradlew bootRun --args='--spring.profiles.active=load'
```

`load` 프로파일이 아니면 안 된다. 기본 프로파일은 `ddl-auto: create`라 **재기동마다 시드가 사라지고**, 지표 엔드포인트도 닫혀 있다.

### 2. 계정을 만든다 (앱이 뜬 뒤 한 번만)

```bash
./load-test/seed/accounts.sh
```

비밀번호 해시는 의도적으로 느린 연산이라 **부하 반복 안에서 만들면 그것이 병목으로 잡힌다.** 그래서 계정 생성은 측정 밖에서 한 번만 한다.

### 3. 측정용 데이터를 넣는다 (측정 회차마다)

```bash
./load-test/seed/fixture.sh
```

경매 시각을 실행 시점 기준으로 다시 계산하므로 **회차마다 다시 돌린다.** 안 돌리면 이전 회차의 경매가 이미 마감돼 있다.

### 4. 측정 전 스냅샷

```bash
./load-test/collect.sh before
```

### 5. 시나리오 실행

본 측정 전에 스모크를 먼저 돌린다. 계정 2~5개로 파이프라인이 끝까지 도는지만 본다.

```bash
ACCOUNT_COUNT=3 k6 run load-test/scenarios/smoke.js
```

통과하면 본 측정으로 간다.

```bash
k6 run load-test/scenarios/a-close-spike.js
```

### 6. 측정 후 스냅샷

```bash
./load-test/collect.sh after
```

### 7. 결과 기록

`load-test/results/TEMPLATE.md`를 복사해 채운다. 빈칸이 있으면 그 회차는 비교 대상이 못 된다.

## 시나리오

- **A. `a-close-spike.js`** — 경매 1건에 동시 50 → 100 → 200명. 입찰 잠금이 이 규모에서 성립하는지
- **B. `b-close-fanout.js`** — 입찰자가 붙은 경매 여러 건을 같은 초에 마감. 낙찰 팬아웃이 스케줄러 스레드를 얼마나 잡는지
- **D. `d-mixed-baseline.js`** — 조회 위주 + A를 10%. 평상시 응답과 세션 저장소 왕복 횟수

### 부하 모델은 폐쇄형으로 시작한다

기본은 `ramping-vus`다. 가상 사용자가 각자 "요청 → 응답 대기 → 다음 요청"을 반복하는 방식이고, 마감 직전에 사람이 화면을 보고 누르는 상황에 가깝다.

**대신 이 방식에는 함정이 있다.** 서버가 느려지면 사용자가 응답을 기다리느라 다음 요청을 안 보내서, **요청률이 저절로 줄어든다.** 서버가 무너지는 중에도 그래프가 완만해 보이고, 대기열이 자라는 현상 자체가 관측에서 사라진다.

그래서 `hikaricp.connections.pending`이 쌓이는 게 보이면, 그때 `constant-arrival-rate`(서버 상태와 무관하게 초당 N건을 밀어 넣는 방식)로 한 번 더 돌린다. 대기가 자라는 모습은 그쪽에서만 드러난다.

## 로컬에서 속지 않는 법

- **앱 인스턴스는 하나만 띄운다.** 둘이 같은 DB를 보면 진행 스케줄러가 각각 돌아 같은 경매를 두 번 마감하려 들고, 낙찰 팬아웃도 두 번 일어난다. 시나리오 B가 재려는 값이 통째로 무의미해진다. `collect.sh`와 시드 스크립트가 경고를 띄우지만 **막지는 않으므로** 직접 확인한다
- **워밍업은 시나리오로 갈라져 있다.** `phase:warmup`과 `phase:measure` 태그가 붙고, 집계는 `measure`만 본다. `stages`로 붙여 두면 JIT 컴파일 전 값과 커넥션 풀 예열 전 값이 같은 지표에 섞여 사후에 걸러낼 수 없다
- **`options`에 `responseCallback`을 적는 방식은 k6에 없다.** 그렇게 쓰면 조용히 무시되고 정상 거절(400)이 실패율에 섞인다. `lib/bid.js`의 `treatRejectionAsExpected()`가 `http.setResponseCallback`으로 등록한다
- **k6와 앱이 같은 CPU를 나눠 쓴다.** k6 요약의 `dropped_iterations`가 0이 아니면 도구가 먼저 한계에 걸린 것이고, **그 회차 숫자는 버린다.** 사용자 수를 절반으로 줄여 같은 형태가 나오는지 대조한다
- **워밍업 30초는 버린다.** JVM은 처음 수천 번 실행 후에야 기계어로 컴파일하고, 커넥션 풀도 그때까지 예열 중이다
- **`Innodb_row_lock_time_avg`는 누적값이다.** 서버 기동 이후 전체 평균이라 한 번만 보면 의미가 없다. `collect.sh`가 전후로 두 번 찍는 이유다
- **한 번에 하나만 바꾼다.** 두 개를 같이 바꾸면 어느 쪽이 효과였는지 영영 모른다
- **거절과 오류를 갈라 센다.** 판매자 본인과 현재 최고가인 사람의 입찰은 **정상적으로** 400이다. 이걸 실패로 세면 오류율이 실제와 무관하게 치솟는다

## 시드 설계에서 일부러 그렇게 한 것들

- **시작가를 1억으로 잡았다.** 최저 상승가 구간표의 마지막 구간(1억 이상 → 50만원)에 들어가서, 가격이 아무리 올라도 구간이 바뀌지 않는다. 덕분에 k6가 상승가를 다시 계산하지 않고 `시작가 + n × 50만`으로 항상 유효한 금액을 만들 수 있다
- **마감을 넉넉히 뒤로 뒀다.** 진행 중인 경매는 정해진 시각에 자동 마감된다. 측정 시간보다 마감이 빠르면 측정 중간에 대상이 사라진다. 시나리오 B는 반대로 이 자동 마감을 **일부러 이용한다**
- **경매 상태를 `SCHEDULED`로 넣는다.** 입찰 판정은 상태가 아니라 서버 시각을 보고, 진행 스케줄러가 다음 틱에 알아서 `IN_PROGRESS`로 옮긴다. 상태를 손으로 맞춰 넣으면 스케줄러가 하는 일을 측정에서 빼는 셈이 된다
- **계정을 API로 만들고 나머지는 SQL로 넣는다.** 비밀번호 해시는 서버가 만들어야 로그인이 되므로 계정만 API를 탄다. 반면 "진행 중인 경매"는 발행에서 시작까지 최소 1시간 규칙 때문에 **API로는 만들 수 없다**

## 질의 수를 셀 때 (가설 5 회차)

성능 측정과 **같이 돌리지 않는다.** 로그 기록이 디스크 I/O로 응답 시간에 섞인다. 반대로 이 회차는 응답 시간을 안 보므로 로그가 켜져 있어도 된다.

```bash
cd backend && ./gradlew bootRun --args='--spring.profiles.active=load --logging.level.org.hibernate.SQL=DEBUG --logging.level.org.springframework.jdbc.core.JdbcTemplate=DEBUG --logging.level.org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate=DEBUG'
```

- **`show-sql`은 켜지 않는다.** `org.hibernate.SQL=DEBUG`와 같이 켜면 같은 SQL이 표준 출력과 로거로 두 번 나가 **질의 수가 그대로 두 배가 된다.** `load` 프로파일이 `show-sql: false`라 로거만 켜면 된다
- **JDBC 로거를 반드시 같이 켠다.** 목록 조회의 본 질의는 `AuctionListRepository`가 `NamedParameterJdbcTemplate`으로 직접 날려서 Hibernate 로거에 전혀 안 잡힌다
- 세는 것은 요청 스레드(`nio-8080-exec`)가 낸 질의만이다. 경매 진행 스케줄러가 0.5초마다 질의 셋을 내는 배경 소음을 스레드 이름으로 가른다
