# 측정 회차 기록

회차 하나당 이 파일을 복사해 채운다. **빈칸이 있으면 그 회차는 비교 대상이 못 된다.**

## 회차

- 이름 —
- 일시 —
- 커밋 SHA —
- 시나리오 — A / B / D 중
- 이 회차에서 바꾼 것 (한 줄) —
  - 한 번에 하나만 바꾼다. 두 개를 같이 바꾸면 어느 쪽이 효과였는지 영영 모른다.

## 측정 환경

- 실행 위치 — 로컬 / 배포
- 부하 도구가 도는 곳 —
- `dropped_iterations` —
  - **0이 아니면 이 회차는 버린다.** 부하 도구가 먼저 한계에 걸린 것이라 서버 숫자가 아니다.

## 응답

- 입찰 p50 / p95 / p99 —
- 공개 조회 p50 / p95 (시나리오 D) —
- 인증 조회 p50 / p95 (시나리오 D) —
  - 두 값의 차이가 인증 단계 비용의 방향이다. 로컬에서는 왕복이 0에 가까워 작게 나오는 게 정상이다.

## 오류

- 400 거절 건수 —
  - 판매자 본인·현재 최고가인 사람의 입찰이다. **정상 동작이므로 실패가 아니다.**
- 5xx 건수 —
  - 0이 아니면 그 자체가 결함이다. 응답 본문을 함께 남긴다.

## 자원

- `hikaricp.connections.pending` 최대 —
  - 0이 아니면 **커넥션 풀 10이 상한**이라는 직접 증거다 (가설 3).
- `hikaricp.connections.usage` p99 —
  - 커넥션 보유 시간이고 곧 트랜잭션 경계의 폭이다.
- `tomcat.threads.busy` 최대 —
- `jvm.memory.used` 최대 / GC pause —

## 잠금 (전후 차분)

- `Innodb_row_lock_waits` before → after —
- `Innodb_row_lock_time_avg` before → after —
- `Innodb_row_lock_time_max` before → after —

## 세션 저장소 (횟수만)

- 인증이 필요한 요청 수 —
- `cmdstat_get:calls` —
- `cmdstat_ttl` 또는 `cmdstat_pttl:calls` —
- 요청 1건당 왕복 횟수 —
  - **이 값이 이번 측정의 산출물이다.** 횟수는 코드의 성질이라 환경이 달라져도 같다.
- `cmdstat_expire:calls` (갱신이 도는 비율) —

## 마감 지연 (시나리오 B)

- 경매별 지연 ms —
- 지연이 순번에 선형인가 —
  - 선형이면 팬아웃이 스케줄러 스레드를 순서대로 점유하고 있다는 뜻이다 (가설 2).
- `경매 진행 틱 초과` 로그 건수 / 최대 ms —
- `executor.active{name=auctionProgressTaskScheduler}` —

## 가설 대조

- 가설 1 (잠금 구간에 알림) — 정황 넷이 함께 움직였나
  - 잠금 대기 상승 / 커넥션 보유 p99 상승 / 입찰 p99 계단식 / 알림 적재가 입찰에 비례
  - **직접 증명은 이 이슈 밖이다.** 여기서는 "의심된다"까지가 정직한 결론이다.
- 가설 2 (팬아웃 스케줄러 점유) — 확정 / 반증 / 판단 보류
- 가설 3 (커넥션 풀 상한) — 확정 / 반증 / 판단 보류
- 가설 4 (세션 왕복 횟수) — 요청당 몇 회
- 가설 5 (조회 N+1) — 별도 회차에서 확인
