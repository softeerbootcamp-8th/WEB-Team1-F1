### 예상 못 한 발견

**입찰 부하만으로 마감 확정이 밀린다.** 시나리오 A에서 마감된 경매가 하나도 없는데 `경매 진행 틱 초과`가 186회, 최대 2,348ms 찍혔다. 진행 스케줄러도 커넥션 풀에 줄을 서기 때문이다.

마감 지연의 원인이 **둘**이라는 뜻이다 — 팬아웃(B에서 확인)과 커넥션 경합(A에서 확인). 실제 마감 시각에는 입찰도 몰리므로 둘이 동시에 걸린다.

### 측정에서 배운 것

- **게이지는 실행 중에 찍어야 한다.** 처음엔 끝난 뒤 찍어 `pending=0`이 나왔고, 그대로였으면 가설 3을 정반대로 판정할 뻔했다. `sample.sh`가 이래서 생겼다
- **정상 거절은 400이 아니라 409다.** `BidErrorCode`에서 확인했다. 400·403·404는 오히려 스크립트나 시드가 틀렸다는 신호라 따로 센다
- **`options`에 `responseCallback`을 적는 방식은 k6에 없다.** 조용히 무시되고 409가 실패율에 섞인다
- **질의를 셀 때 `show-sql`과 `org.hibernate.SQL=DEBUG`를 같이 켜면 안 된다.** 같은 SQL이 두 번 나가 질의 수가 그대로 두 배가 된다
- **Hibernate 로거만으로는 질의의 절반을 못 본다.** 목록 조회의 본 질의는 `NamedParameterJdbcTemplate`으로 나가서 안 잡힌다. JDBC 로거도 같이 켜야 한다
